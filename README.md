# ansipeek

**颜色是数据，不是装饰。**

`ansipeek` 读取一段终端输出，把里面的 ANSI 转义序列逐个拆开来讲清楚：
每个序列是什么类型、什么含义、对应哪段文字；然后把纯文本还原出来。

- 零依赖，Python 3.10+ 标准库即可运行
- 单文件，`ansipeek.py` 拷走就能用
- 不联网、不写文件

## 为什么需要它

从 CI 捞一段日志下来想搜一个错误码，搜不到——因为那行字被一串颜色码切成了好几段。
肉眼看着是连着的，字符串匹配却对不上：

```
\x1b[31mERROR\x1b[0m: connection refused
```

`ERROR` 在原文里前后都粘着转义码，直接搜 `ERROR` 反而可能匹配到。
把它还原成 `ERROR: connection refused`，搜索、比较、统计就都正常了。

`ansipeek` 做两件事：**把序列讲清楚**，以及**把文本还原**。

## 用法

```bash
# 分析一个文件
python ansipeek.py --input sample.txt

# 从管道读，只输出还原后的纯文本
cat sample.txt | python ansipeek.py --plain

# 机器可读输出
python ansipeek.py --input sample.txt --json
```

输出：

```
原始长度: 33 字符
纯文本长度: 25 字符
转义序列: 4 个，占 8 字符

序列明细：
    1. [CSI] \e[31m  →  前景 红
    2. [CSI] \e[1m   →  加粗
    3. [CSI] \e[0m   →  重置全部属性
    4. [CSI] \e[0m   →  重置全部属性

颜色使用（按出现次数）：
  重置全部属性              出现 2 次（代码 0）
  前景 红                   出现 1 次（代码 31）

还原后的纯文本：
----------------------------------------
ERROR: connection refused
```

JSON 输出里每条序列带 `raw`（原始串）、`kind`（CSI / OSC / ESC）、
`description`（可读说明）和 `text_offset`（在纯文本中的位置）。

## 支持的序列类型

| 类型 | 形式 | 处理方式 |
|---|---|---|
| CSI | `ESC [ 参数 中间符 最终字节` | 按最终字节分派：SGR 颜色、光标移动、清屏等 |
| OSC | `ESC ] ... BEL` 或 `ESC ] ... ESC \` | 识别窗口标题，其余标记为 OSC 扩展 |
| ESC | `ESC + 单字符` | 记录为单字符转义 |

SGR 参数会被翻译成中文说明：`31` → 「前景 红」、`1` → 「加粗」、
`44` → 「背景 蓝」、`0` → 「重置全部属性」。

颜色统计按出现次数排序，同时记录每种颜色**第一次出现的位置**，
这样可以看出输出的配色结构，而不只是数出有几种颜色。

## 已知局限

- **只处理 ANSI 转义**，不解析终端的私有模式序列（如 `ESC[?25l` 隐藏光标）里的语义，只记录其存在。
- **不处理回车覆盖**。像进度条那样用 `ESC[2K` 原地刷新的输出，工具只还原字符、不还原屏幕最终状态。
- **不还原颜色语义**。它只说「这里是前景红」，不评价这个配色好不好看。
- **OSC 的内容只做有限识别**，除窗口标题外的 OSC 扩展统一标为「OSC 扩展」，不逐个解释。
- **按字节而非屏幕列处理**。全角字符、双宽字符的显示宽度不在考虑范围内。

## 为什么还要做这个

终端输出的处理方案大多分成两派：要么完整实现一个终端模拟器（重，但能还原屏幕），
要么粗暴地删掉所有非打印字符（轻，但丢信息）。

`ansipeek` 站在中间：它不模拟屏幕，只**把序列翻译成人能读的话**，
同时给出一个确定的纯文本版本。多数时候你要的就是后者——
一份能被搜索、能被比较的文本，而不是一个可以回放的全屏终端。
